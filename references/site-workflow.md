# 整站优化工作流

适用于通用 Shopify Liquid 主题。拿到源码目录和真实预览地址后开始；主题 ZIP 先解压。不要求特定主题品牌。

默认单 agent，按 [执行预算](execution.md) 使用 batch；模型先读摘要，必要时定点读取原始证据。新增候选不超过预算轮数，连续低收益即停止该路径并明确未达标；停止不等于验收通过。

1. **建立范围与基线。** 读取主题约定和已有改动，记录主题 ID/源码版本、页面实例、业务状态和测试环境。首页、代表商品页、集合页及关键内容模板分别列出实际 URL，不猜 handle。使用 [基线表](../assets/templates/01-baseline.md)。
2. **复用基线，缺什么补什么。** 先读已有 run 摘要、源码指纹和预览身份，检查引擎/配置、页面与内容状态是否可比；保留原警告，不能把同一份样本复制为新测量。可比的现有基线直接复用，只有缺失、漂移、环境不可比或用户明确重测才补测。scan 离线建立模板、资源、依赖和候选清单。没有线上基线就不能声称可提多少分；探索允许先测代表页面3次，完整正式基线仍每组至少5次。
3. **定位影响分数的代码。** 从实际 LCP/FCP/TBT/SI 和阻塞链回到文件、函数、调用者、执行时机：优先检查初始执行的无效工作、重复绑定/初始化、布局读写、屏外计时器、共享 CSS/字体发现与 Liquid 资源输出。源码模式不是耗时证明，静态规范数量不是优化收益。先用已有 LHR、scan/map 和源码；只有缺少运行证据才定点 capture/profile。不要默认展开全站素材下载、全部 App 排查或规范清零。明确受影响页面、可验证假设与必要回归后进入补丁，不能停在泛化建议。
4. **生成并审阅小批补丁。** plan-site 接收明确 recipe。图片策略可在支持的结构内生成；JS/CSS/Liquid 提供已审阅候选。保留素材、文案、布局、schema、header 和功能；不能以关闭必要 App、删商品图或改播放行为换分。
5. **应用与同步候选。** apply 前检查 diff、源指纹和验证要求；保存 receipt。确认本地修改已进入实际预览，记录候选主题身份。工具不运行 Shopify push/publish。
6. **先小范围验证收益。** 用现有脚本验证受影响行为；生命周期改动才扩到多实例/卸载重连，布局、CSS、图片属性改动才加对应断点截图。保留原内容、功能与清晰度，不默认重跑所有套件。确认候选预览版本后，先对受影响代表页/设备跑 exploration（默认3次），与基线全部可比样本比较，记录所有候选历史。无收益或回归则修复/回滚，不扩大成40次测量。出现可信收益后再跑完整正式候选矩阵并 verify-site；探索数据不能代替正式验收。capture/scenarios 的写请求限制不能证明真实业务写操作通过。
7. **保留或继续优化。** 各页各设备达到门槛且功能/画面满足约定，才形成 [交付记录](../assets/templates/04-results.md)。未达标时仅在可操作且有收益证据、预算允许时继续迭代；预算耗尽或低收益时停止新增候选并交付未达标结论；出现回归就修复或 rollback。若瓶颈来自平台或第三方，明确受限证据和需要的业务决定。

默认移动最低 75/中位 80，桌面最低 85/中位 90。整站通过只覆盖配置中实际测过的页面矩阵；不覆盖所有动态 URL，也不保证以后每次测试相同。详细命令见 [命令参考](commands.md)，环境与证据见 [测量约定](measurement.md)。

优化交付先列实际修改的文件/代码路径、对应瓶颈、同条件分数变化、回归结果与保留/回滚决定。没有代码修改时直说“本轮仅诊断”，不能用报告数量冒充优化。已有规范告警、既存功能问题和本次新增回归分别记录；不为清理无关历史告警持续扩展本轮任务，也不隐藏它们来宣称全站验收通过。
