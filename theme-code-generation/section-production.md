# 日常 Section 生产规范

版本：1.1（试行）  
官方文档核验日期：2026-10-20

用于从需求、设计或参考组件生成 Section，以及给已有 Section 增加能力。生成第一版时就执行本规范；最终检查使用同技能的 [theme-code-generation.md](theme-code-generation.md)。该文档也是复杂度、嵌套、行数和重复片段预算的唯一来源。

## 1. 官方依据与项目实现选择

| 来源类型 | 官方依据 | 在生产中的落实 |
| --- | --- | --- |
| OFF-PLATFORM | [Section schema](https://shopify.dev/docs/storefronts/themes/architecture/sections/section-schema)：Section 只有一个 schema，内容为有效 JSON，不在其中求值 Liquid，也不能嵌套在其他 Liquid 标签内 | schema 与实际输出一起设计；需要在编辑器添加的普通 Section 配置有效 presets；固定用途 Section 按目标主题接入方式处理 |
| OFF-PLATFORM | [Section blocks](https://shopify.dev/docs/storefronts/themes/architecture/blocks/section-blocks)：Section 可以定义自己的内容块 | 重复的可编辑单元采用目标主题支持的 blocks 方式，不预设所有主题都使用同一块架构 |
| OFF-GUIDE | [编辑器集成](https://shopify.dev/docs/storefronts/themes/best-practices/editor/integrate-sections-and-blocks)：编辑器会动态更新 Section，并提供区块标识与生命周期事件 | 输出适当的 block 标识，初始化与清理配合动态挂载；隐藏面板中的 block 被选中时能够显示 |
| OFF-PLATFORM | [原生 JS/CSS 标签](https://shopify.dev/docs/storefronts/themes/best-practices/javascript-and-stylesheet-tags)：标签内不求值 Liquid，打包脚本不按实例重复注入 | 实例配置放在实例 DOM 数据中，不在静态脚本里插入 `section.id` |
| OFF-GUIDE | [性能实践](https://shopify.dev/docs/storefronts/themes/best-practices/performance)与[可访问性实践](https://shopify.dev/docs/storefronts/themes/best-practices/accessibility) | 生成时确定媒体优先级、必要交互、键盘操作与语义结构，不能只把这些项目留给检查器 |

以下带 `PROJ-GEN` 的组织方法和默认选择是项目约定，不是 Shopify 平台强制架构。明确的用户需求和目标主题契约优先；不得为了本规范改变设计目标。

## 2. 落笔前确定生产方案（PROJ-GEN-01）

先阅读目标主题的相近 Section、实际调用的 snippets、样式 token 和 JS 初始化机制。不要只根据文件名猜接口。用以下信息形成简短方案；可以写在工作说明中，不强制创建额外文件或等待用户批准：

| 要确定的内容 | 生成前作出的具体决定 |
| --- | --- |
| 功能边界 | 此 Section 做什么、重复单元是什么、是否确实需要 JS |
| 接入方式 | 新增还是修改；单文件粘贴还是多文件主题集成；是否需要编辑器添加入口 |
| 主题复用 | 已确认可用的容器、字体、配色、按钮、卡片、图片与事件接口 |
| 内容模型 | 数据对象、section settings、blocks 分别承载哪些数据 |
| 配置与空状态 | 每个设置作用在哪里；未选图片、空文案、无 blocks 时怎么显示 |
| 结构与预算 | 文件职责、预计体量、控制流深度；较复杂部分的独立职责 |
| 运行状态 | 多实例、移动端、编辑器重载、键盘与媒体加载策略 |

主题不可用时生成通用实现，明确没有验证特定主题接口；不要引用猜测存在的 snippet、全局变量或主题 CSS 类。单文件交付允许在一个 Section 中组织标记、静态 CSS 和必要 JS，仍按区域预算控制体量。多文件方案必须完整交付并接好依赖。

## 3. 先建内容模型，避免从第一版开始复制（PROJ-GEN-02）

- 可增删、排序的卡片、优势项、问答、幻灯片等，从第一版采用 blocks 或实际业务数据循环。不要生成 `title_1` 至 `title_12` 和十二套相同标记。
- 固定且职责不同的主标题、副标题、主按钮可以使用独立设置；不为形式统一强行改成 blocks。
- 沿用目标主题的 local section blocks 或 theme blocks 架构；不要把两套渲染模式随意混合。数据来自商品/集合等对象时，不再复制成一套需要人工同步的配置。
- 先复用已有 snippet；需要新 snippet 时明确输入、输出和作用域。相同视觉但不同业务含义的片段先比较职责，避免用大量开关制造通用组件。
- 每种重复单元只维护一份标记；桌面和移动端优先共享结构。确有不同 DOM 要求时说明依据，并隔离 ID、焦点和事件。

示例：需求为“可增删的优势列表”，应先确定 `item` block 的 `title` / `body` 字段，再写循环；不是先生成三张静态卡片再做参数化。以下仅示范标记，配套 schema 需要定义相同类型和字段：

```liquid
<ul class="feature-list__items">
  {% for block in section.blocks %}
    <li class="feature-list__item" {{ block.shopify_attributes }}>
      {% if block.settings.title != blank %}
        <h3>{{ block.settings.title | escape }}</h3>
      {% endif %}
      {% if block.settings.body != blank %}
        <div class="feature-list__body">{{ block.settings.body }}</div>
      {% endif %}
    </li>
  {% endfor %}
</ul>
```

这里的 `body` 应定义为 richtext；如果定义成普通 text/textarea，则按文本输出并转义。实际标题层级取决于页面上下文；多个 block 类型时采用相应分派，不能让该示例错误渲染其他类型。

## 4. 配置跟随真实用途生成（PROJ-GEN-03）

先列“字段 → 类型 → 渲染位置 → 默认/空状态”，再同步写 schema 和绑定：

- 主题已有字号、颜色方案、容器宽度、按钮样式时优先复用。只有运营确实需要独立调整时才新增控件，不默认给每个元素生成颜色、字号、圆角和间距全套设置。
- 显示语言和翻译方式沿用主题；无目标主题且用户无指定时，运营标签默认中文，字段 ID 使用稳定的语义化名称。
- 重复单元的内容设置属于 block；整体布局设置属于 section。不要仅为绕过顶层设置计数把整体配置搬进 blocks。
- 字段引用、类型、范围与 preset 保持一致。新设置必须实际生效；删除配置前检查持久化使用。已有 setting ID、block 类型和 preset 不因清理代码随意改名。
- 图片、视频、商品等使用相应资源选择器；不把预览资源对象或参考站 URL 硬编码进 schema 默认值。
- 无链接时不生成空 `href` 或 `javascript:void(0)`；导航使用链接，切换/展开等动作使用按钮。空图片采取稳定占位或隐藏媒体区域的明确策略。
- 默认内容、空状态和真实商店内容分开；演示文案不能悄悄成为既有主题的业务文案。

## 5. Liquid 从结构上保持简洁（PROJ-GEN-04）

编写顺序通常为：必要的值准备 → 有语义的容器 → 单份重复单元循环 → 必要状态分支。不要给所有层都增加“开关存在且不为空”的保护判断。

复用条件或值时采用合法的 Liquid 赋值/分支方式，避免重复读取复杂表达式；不把只用一次的所有字段机械复制成几十个别名。没有语言依据时不要在 `assign` 中构造比较表达式或 JavaScript 风格布尔语法。

控制流新增部分优先保持共享规范的浅层目标；写到继续嵌套才能扩展时，先考虑收敛分支、提取独立职责。合并条件前检查 Liquid 求值顺序、空值和副作用，不能凭缩进推断等价。

按输出上下文转义普通文本和属性；richtext 按其类型处理，JS 数据用适合该上下文的序列化与转义，不直接把文案拼进可执行代码。动态 URL 使用主题/平台对象和实际配置，不自行拼接固定语言或商店域名。

## 6. CSS 在生成时约束作用域和体量（PROJ-GEN-05）

- 使用稳定组件前缀和局部选择器，沿用主题 token。不要生成全局 `h2`、`button`、`.card` 等覆盖规则影响其他区块。
- 布局使用 Grid/Flex 等适当方式和必要断点；按内容与容器设计响应式，不靠不断追加媒体查询和覆盖声明修补第一版。
- 同一状态/断点集中组织；优先修改原声明，不连续堆叠同选择器和 `!important`。不同回退值和层叠位置不算可直接删除的重复。
- 静态样式遵循目标主题的原生 stylesheet 或 asset 组织方式；不因行数预算强制全量外置。
- 每实例动态参数通过受约束的 CSS 自定义属性或实例级样式传入。数值来自明确的 range/number 设置并处理单位；不要把任意文本直接拼成 CSS。
- ID 含 `section.id`，需要时再包含 `block.id`，相关 `for` / `aria-controls` / 锚点同步生成。静态类名保持稳定以供共用样式使用。
- 不向每个实例重复写入同一套巨量静态样式；也不为了合并样式破坏原生 stylesheet 的作用域和加载条件。

## 7. JS 按必要交互生成（PROJ-GEN-06）

静态列表、图片文案、普通 Grid 布局默认无需 JS。优先使用合适的原生 HTML/CSS 能力；需要交互时沿用主题已存在的组件机制，不同时再创建第二套全局框架。

生成脚本时直接满足以下契约：

| 环节 | 实现要求 |
| --- | --- |
| 实例输入 | 从本实例 DOM/data 属性读取配置；静态打包脚本中不嵌入 Liquid |
| 初始化 | 普通页面加载和编辑器动态插入都可工作；初始化同一实例两次不会重复绑定 |
| DOM 查询 | 以当前实例为作用域，只有确有理由才使用全局选择器 |
| 清理 | 卸载时清理监听器、观察器、计时器及其他持有实例的资源 |
| 再挂载 | 能重新初始化；不能用残留的 initialized 标记把新实例永久跳过 |
| 编辑器选择 | 轮播/标签等隐藏内容被选中时正确展示；仅实现组件实际需要的事件 |
| 首次操作 | 延迟加载时首个点击仍完成用户预期，处理加载失败和重复触发 |

可用 custom element 生命周期、主题已有控制器或有清理能力的初始化函数实现；不要求每个 Section 都生成一份编辑器全局事件总线。全局注册与事件桥接复用主题机制，避免每个实例再注册一次。

按钮有可访问名称、键盘可用且状态属性与显示一致；弹层等需要管理焦点的组件实现相应行为。动画尊重 reduced-motion。不要复制一套“通用 JS 模板”到没有交互需求的 Section。

## 8. 媒体与性能从第一版明确（PROJ-GEN-07）

使用 Shopify 图片对象与合适的 `image_url` / `image_tag` 等能力，按真实布局设置候选宽度与 `sizes`，提供尺寸/宽高比以稳定布局。不要统一生成最大尺寸图片或同时加载两张 CSS 隐藏的桌面/手机主图。

已确定的首屏/LCP 图片不懒加载；屏外媒体采用合适延迟策略。Section 可在不同位置复用时，沿用主题可靠的位置策略或明确的加载选项；位置未知时保留平台/主题默认行为并说明需确认，不给所有 Section 强行 `eager` / `high`，也不一律 `lazy`。

静态必要内容直接由 Liquid/HTML 输出；不用 JS 再拉取已存在的内容。首屏样式、脚本依赖和初始化时序在代码组织时确定；`defer`、`async`、动态 import 按依赖选择，不能为消除告警统一替换。

## 9. 边生成边收敛，完成后检查（PROJ-GEN-08）

每完成一个主要职责，就用共享预算看是否正在膨胀。发现第三套相同标记、不断增加布尔开关、连续嵌套或反复覆盖 CSS 时，当场调整内容模型或结构，不等完整代码写完才回头拆。

不要求每写一行就运行检查器。完成可用候选后，按共享规范执行 Theme Check、预算复核和受影响功能验证；检查失败时回到具体生成决策修复。

若任务使用 section-snapper：

- 忠实还原时保留已指定的视觉、DOM/样式要求；在允许的参数化范围中采用内容模型与实例隔离。必要的重复或较长 CSS 记录为有依据的例外。
- 用户要求单文件可复制或现有打包器只能交付单文件时，先按该约束组织；不得暗中新增未交付的 snippet/asset。
- 改写模式可按职责重新组织，但仍需满足已约定的设计与交互。
- 采集、预览、对照与发布仍按相关技能执行；本规范没有替它们实现自动接入，也不额外授权联网采集或发布。

交付时简述复用了什么、采用了什么内容模型、实际提供哪些文件、哪些验证已完成。没有 Shopify 预览时，不把本地渲染称为真实主题编辑器验收。
